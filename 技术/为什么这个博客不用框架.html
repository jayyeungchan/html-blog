为什么这个博客不用框架

每次想写点东西，先要 npm install，然后等依赖树解析完，再想起上次升级某个插件把构建搞坏了。等环境终于跑起来，想说的话已经凉了半截。

所以这个博客做了个很朴素的决定：它由 HTML 文件组成，没有别的。没有打包器，没有前端路由，没有运行时依赖，构建脚本只有一百多行，干的事情是把目录翻译成一份 JSON 索引。

一个 HTML 文件能装下多少东西

比想象中多。浏览器原生已经给了大部分我需要的能力：

  • 排版交给 CSS，网格、断点、深浅色都是几行变量的事
  • 路由交给文件系统，/技术/某篇文章.html 就是它自己的地址
  • 数据交给 fetch，读一份构建时生成的索引就够了
  • 交互交给原生 DOM，全站 JS 加起来不到 8KB，没有压缩过

这些能力不会因为我三个月没更新依赖而过期。三年后打开这个仓库，node build.js 依然能跑。

我真正需要的功能只有四个

列出需求之后，事情就变得很清楚了。一个个人博客需要的是：

  1. 按分类浏览，以及一列按时间倒序的文章
  2. 能搜索标题和摘要
  3. 读起来舒服，手机上也是
  4. 加一篇新文章的成本足够低

前三条用静态页面加一份索引就能做到，第四条恰好是这个方案最擅长的部分——新建一个文件，结束。

判断标准不是「框架能不能做」，而是「为了这四件事，我愿意维护多少东西」。当维护成本超过写作意愿时，工具就已经在帮倒忙了。

代价是什么

说清楚成本，才算诚实的方案。放弃框架换来的限制也很具体：

  • 没有组件复用，公共部分靠一份 CSS 和一个注入顶栏的脚本
  • 没有热更新，改完刷新页面，快得也够用
  • 没有类型检查，写错标签只能靠眼睛和构建时的告警
  • 文章是手写的 HTML，不是 Markdown

最后一条值得展开。手写 HTML 听起来很原始，但它换来的是完全的控制权：想在这段话旁边放一个特别的卡片，直接写 div 就行，不需要去查某个主题的扩展语法。

Markdown 让你写得快，HTML 让你写得准。文章少的时候，准比快重要。

什么时候我会换回框架

如果出现下面任意一种情况，我会毫不犹豫地换：需要评论系统并且要自建后端、文章数量超过几百篇需要服务端分页、需要多语言和版本化文档。

在那之前，一个文件夹、一份索引、一个构建脚本，够用了。
